# CMS Specification — Payload at `/dashboard`

Status: **proposed** (2026-10-16), awaiting Mikel's decisions (§10). Supersedes `08` §6 "no CMS" once approved.
Sources checked 2026-10-16: npm registry (`payload` and `@payloadcms/*` versions, peer dependencies) and the Payload docs at tag `v3.90.2` (installation, admin routes, deployment, Postgres, SQLite, storage adapters, authentication, access control, local API).

## 1. Goal

Let Mikel add and edit projects, short entries, Lab entries, images and site text from a private dashboard, with no code, while keeping the public site fast, accessible and statically served.

## 3. Architecture

```
app/
  (frontend)/          ← the current site moves here unchanged
    layout.tsx         ← current root layout (header, footer, fonts, Lenis)
    page.tsx, work/, lab/, about/, not-found.tsx …
  (payload)/           ← generated by Payload, not edited
    dashboard/[[...segments]]/page.tsx   ← admin UI at /dashboard
    api/[...slug]/route.ts               ← REST API (used by the admin)
    layout.tsx         ← Payload's own <html>, styles scoped to the admin
payload.config.ts      ← collections, globals, db, storage, auth
```

- **Route groups** keep the two apps apart: Payload's layout and CSS never touch the public site, and the site's GSAP, Lenis and fonts never load in the dashboard (Payload docs: "a boundary between the Admin Panel and the rest of your application").
- `next.config.ts` is wrapped with `withPayload()` (ESM, which we already use).
- **The public pages read content with Payload's Local API** (a direct database query on the server, no HTTP round trip), replacing today's `content/*.ts` imports. Components stay the same; only `content/index.ts` changes.

### Rendering after the CMS (changes `08` §2)

Today every page is built once and never changes. With a CMS, content changes after deploy, so:

| Route | Today | With the CMS |
|---|---|---|
| `/`, `/work`, `/lab`, `/about` | Static | **Static, revalidated on publish**: a Payload `afterChange` hook calls `revalidatePath()`, so the page rebuilds within seconds of saving |
| `/work/[slug]` | Static, unknown slugs 404 | Static for existing projects; **a newly added project renders on first visit, then is cached**; unknown or unpublished slugs still 404 (`notFound()`) |
| `/dashboard`, `/api/*` | — | **Dynamic, server-rendered** (needs a server) |

Visitors still get pre-rendered HTML from Vercel's CDN; only the dashboard and API run code on each request.

## 4. Database

Payload needs MongoDB, Postgres or SQLite. Vercel has no persistent disk, so the database must be hosted.

| Option | Cost | Fit | Verdict |
|---|---|---|---|
| **Neon Postgres (via the Vercel Marketplace)** | Free tier | Native Vercel integration; Payload's Postgres adapter manages the schema in development and generates migrations for production | **Recommended** |
| Turso (hosted SQLite / libSQL) | Free tier | Works with `@payloadcms/db-sqlite`; separate account | Good alternative |
| MongoDB Atlas | Free tier | Works with `@payloadcms/db-mongodb`; separate account | Fine, but a different data model from the typed relational content we have |

**Environments:** a separate Neon branch for local development/preview and one for production, so testing never touches real content. Migrations (`payload migrate`) run in the Vercel build.

## 5. Media storage

Uploads can't live on Vercel's filesystem. **Vercel Blob** via `@payloadcms/storage-vercel-blob`:
- `clientUploads: true`: files go straight from the browser to Blob. Server uploads on Vercel are limited to 4.5 MB (Payload docs) and renders are often larger.
- Payload generates the responsive sizes; the site keeps using `next/image` (Blob URLs added to `images.remotePatterns`).
- **Export rule kept:** upload web masters (≤ 2560 px, from `pnpm images:export`), not raw 20 MB renders.
- Free-tier limits to verify at setup (storage and transfer); the portfolio's images (~200 × ≤ 600 KB ≈ 120 MB) should fit.

## 6. Content model (mirrors today's TypeScript types)

### Collections

| Collection | Fields (summary) | Notes |
|---|---|---|
| **Projects** | kind (case study / short entry), title, slug (auto from title, editable), order, product name, summary (≤ 160, enforced), year, date, course, institution, collaboration (approved wording), context, company, featured, team (array), my role (array, min 1), tools, fields (multi-select), hero + card image (required), process tiles (3, case studies only), **sections** (case studies) or **body + media** (short entries) | Field visibility switches with *kind* (Payload conditional fields) |
| ↳ Section **blocks** | Image · Image grid · CAD/Render compare · Annotated image (annotation rows with x/y %) · Spec table · Bar chart · Step sequence | One Payload block per existing media module, so the editor builds sections from the same pieces the site already renders |
| **Lab entries** | id (L-###), title, type, date, images (1–4), note, related project (relationship), link | |
| **Media** | file, **alt text (required)**, caption, credit (Mikel / team / name), placeholder (checkbox) | `check:placeholders` reads this flag |
| **Users** | email, password, name | Admin only (§7) |

### Globals (single documents)

| Global | Content |
|---|---|
| **Site** | name, role, headline, supporting text, availability, sign-off, location, email, LinkedIn, education, languages |
| **Homepage** | process grid label, title, lead, CTA text; approach steps |
| **About** | intro, "How I work" paragraphs, tools table |
| **Lab page** | intro, "Currently exploring" interests |

### Editorial features
- **Drafts and versions** (Payload built-in): save without publishing, restore earlier versions. Replaces our `status` field; only *published* documents reach the site.
- **Live preview** of a draft project on the real page layout (Payload Live Preview), behind authentication. Optional; see §10.
- **Validation** carried over from the type system: required alt text, summary length, at least one role line, three process tiles for featured case studies.

## 7. Authentication and security

| Measure | Setting |
|---|---|
| Admin route | `routes.admin: "/dashboard"` |
| Who can log in | One `users` collection, admin users only; **no public sign-up** (`create` restricted to logged-in admins) |
| First account | Created **by Mikel** on Payload's first-run "create first user" screen, with his own password (I don't set real credentials) |
| Brute force | `maxLoginAttempts: 5`, `lockTime: 10 min` |
| Session | Server sessions (revocable, Payload default `useSessions: true`), HTTP-only `Secure` `SameSite=Lax` cookies, `tokenExpiration: 2 h` |
| Secrets | `PAYLOAD_SECRET` (long random value) and `DATABASE_URI`, `BLOB_READ_WRITE_TOKEN` as Vercel environment variables; never committed (`.env*` already ignored) |
| API surface | REST API only for the admin; public `read` limited to published documents; all writes require an admin. **GraphQL disabled** (`graphQL.disable: true`) |
| Search engines | `/dashboard` and `/api` set `noindex`; excluded from the sitemap; disallowed in `robots.txt` |
| Password reset | Needs an email provider (§10); without one, reset happens by an admin in the dashboard |
| Optional hardening | Vercel Firewall rate-limit rule on `/api/users/login`; 2-factor auth is not built into Payload (would need a plugin): out of scope for v1 |
| Dependency hygiene | Payload moves fast (weekly releases): pin the version, `pnpm audit` before each deploy, read release notes for security fixes |

## 8. Migration of today's content

1. A one-off **seed script** (`pnpm seed`) reads the current `content/*.ts` files and creates the matching Projects, Lab entries, globals and Media (uploading the current images, keeping their placeholder flag) in the **development** database.
2. Mikel reviews in `/dashboard`; then the same script runs once against production.
3. `content/*.ts` files are deleted; `content/types.ts` is replaced by Payload's generated types (`payload generate:types`), so components stay type-safe.
4. The Playwright suite runs against a seeded test database (test credentials from a local `.env.test`, never real ones).

## 9. Effect on the plan

| Area | Impact |
|---|---|
| Public site look, motion, URLs | None |
| Public JS | None (the admin bundle loads only under `/dashboard`) |
| Performance | Same CDN-served HTML; first visit to a brand-new project renders once on the server |
| Build | Longer (Payload + migrations) |
| Accounts Mikel creates | Neon (via Vercel Marketplace, one click), Vercel Blob (one click), optionally an email provider |
| Monthly cost | €0 on free tiers at this traffic |
| Time | **About 4–6 working days**: install and restructure (1), collections, blocks and globals (1.5), switch the site to the Local API plus revalidation (1), seed and migrate (0.5), auth hardening, tests and docs (1) |
| Deadline (≈ 15 Dec) | Fits if started now: Mikel could then enter case-study copy and images himself for Checkpoint B |

**Alternative considered:** a Git-based CMS (Keystatic, TinaCMS) keeps the site 100% static with no database, saving changes as commits. It's simpler and has fewer moving parts, but Payload gives a real dashboard with drafts, versions, an upload library and room to grow, which is what was asked for.

## 11. Implementation notes (2026-10-16)

- **Layout:** the site moved to `app/(frontend)/`, Payload's generated files are in `app/(payload)/`, the CMS schema in `cms/` (collections, globals, media blocks, access, revalidation) and `payload.config.ts`. Two root layouts, so unmatched URLs use `app/global-not-found.tsx` (Next's experimental `globalNotFound`), which reuses the site's header, footer and 404 content.
- **Data layer:** `content/index.ts` reads with the Local API and maps documents to `content/types.ts`. That file stays as the site's view model instead of being replaced by `payload-types.ts` (§8.3): components keep a narrow, validated shape and don't change when the dashboard schema does. Production shows published documents only; `pnpm dev` also shows drafts.
- **Images:** Media uploads get a 10 px WebP blur preview on upload (stored on the document), so `next/image` keeps its blur-up. Locally files live in `media-uploads/`; with `BLOB_READ_WRITE_TOKEN` set, Vercel Blob serves them directly (`disablePayloadAccessControl`, media is public). Alt text "decorative" maps to an empty `alt`.
- **Also editable (beyond §6):** homepage hero image and its callouts, and the Approach heading.
- **Rendering:** pages are prerendered at build (which therefore needs the database) and revalidated by `afterChange`/`afterDelete` hooks. `/work/[slug]` dropped `dynamicParams = false`; unknown slugs still 404 through `notFound()`.
- **Search engines:** `/dashboard` and `/api` are disallowed in `robots.txt`, send `X-Robots-Tag: noindex, nofollow` and are not in the sitemap.
- **Local database:** `pnpm db:dev` runs Postgres 17 from `embedded-postgres` on port 5433 (UTF-8; databases `portfolio` and `portfolio_test`). Development pushes schema changes automatically; production uses migrations in `migrations/`, applied by the Vercel build command (`pnpm payload migrate && pnpm build`).
- **Seed:** `pnpm seed` imports `content/seed/` (the former typed content) and is idempotent. The Vercel build runs it with `SEED_IF_EMPTY=1`, so a new production database is filled once (the database variables are *Sensitive* and can't be pulled to a PC) and later deploys skip it. `PAYLOAD_DB_PUSH=false` keeps the production schema under migrations only. A small Node loader (`scripts/image-loader.mjs`) lets those files' image imports run outside Next.
- **Tests:** Playwright seeds `portfolio_test`, builds and serves against it, so dashboard edits on the development database never break the suite. No credentials are involved (the tests only read public pages).
- **`check:placeholders`** now lists Media documents with *placeholder* ticked.
- **`package.json`** is `"type": "module"` (as in Payload's template), needed for the Payload CLI to load the TypeScript config.
- **Variable names:** the config reads `DATABASE_URI` locally or `DATABASE_URL` (Neon's Vercel integration).
- **Audit (2026-10-16):** pnpm overrides patch Payload's transitive `undici` (7.30.0) and `dompurify` (3.4.16). Two advisories remain, neither reachable at runtime: `esbuild` ≤ 0.24.2 inside `drizzle-kit` (affects esbuild's own dev server, which isn't used) and `braces` 3.0.3 in Sass's file watcher (no patched release published yet). Recheck before launch.
